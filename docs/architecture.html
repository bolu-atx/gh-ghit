ghit · terminal viewer for GitHub issues + PRs · onboarding brief

Fetch on threads.
Render in one place.

ghit is one Rust binary. It shows GitHub issues and PRs in a terminal. It uses the gh CLI and token GraphQL. The UI loop is synchronous. Worker threads do network I/O. Channels carry results back. This page maps the code for new senior engineers.

01Layers, top to bottom

Dependencies point one way. The UI never fetches. Input never draws. Pure logic never touches the network. Learn this diagram first.

The invariant that mattersDependencies flow one way: ui / input → app → github → api | gh | cache. core / model stay pure helpers beside everything. A new network path follows four steps. Add it in api.rs. Expose it in github.rs. Spawn a thread in app.rs. Poll the channel each frame. Never fetch from ui.rs.

02The frame loop

ratatui is synchronous. Each iteration draws the screen. It then reads one input event. It then polls each channel with a non-blocking try_recv. The loop never waits for the network. Select a step to trace it.

loop {
  terminal.draw(|f| ui::render(f, app))?;      // a — full repaint, record body_rows + rects
  if event::poll(100ms)? { match event::read()? {
    Key(k)   => input::handle_key(app, k),     // b — input mutates App only
    Mouse(m) => input::handle_mouse(app, m),   //     hit-test against last frame's rects
  }}
  poll_bootstrap(app); poll_sections(app);     // c — try_recv, never blocks
  poll_issues(app); poll_board(app); poll_details(app);
  if app.quit { return Ok(()) }              // e
}
Why 100ms100ms bounds input delay and frame cost. It needs no timers. Without data, the loop idles in poll. With data, the next frame picks it up. The board uses this. It opens at once with an empty frame. Cards fill in over later frames.

03Background fetch, one shape

Every network path uses the same pattern. The channels are the concurrency model. There is no executor and no task table. Each fetch kind owns one mpsc pair.

UI thread — app.rsIt creates (tx, rx). It stores rx on App. It spawns a std::thread with tx and cloned args. It returns at once. The modal shows an empty frame.

Many threads, no executor

Board details spawn one thread per card. detail_pending guards each number so it fetches once. Warm cache hits skip the network through BoardDetail::from_issue. Cards fill in over time. No join is necessary.

Failure is a string

Each fetch returns Result<T, String>. If the network, auth, or repo fails, the app shows a status line note. The note expires after 4 seconds. The TUI stays up. Clicked rows still appear in the list.

05Decisions you inherit

The codebase already made four decisions. Understand the reasons before you propose alternatives.

Sync ratatui, no tokio

draw() blocks and returns. No await exists. The network is blocking too (ureq, subprocesses). An executor would only wrap spawn_blocking. Five channels and one thread per fetch cover the load. Revisit this only if the stack goes fully async.

Threads over tasks

The fetch count is small: one board, N issues, N details. Each fetch waits on I/O. One thread per fetch is simpler than a runtime. A pending set stops duplicates. Each thread sends once, exits, and the next frame polls.

gh.rs is end-of-life

All issue and PR reads use token GraphQL in api.rs. Only the project board still shells out. The port path is marked. Reimplement fetch_board in api.rs. Keep the one board_via_gh shim in app.rs as the seam. Then delete gh.rs.

Theme is functions

Render code holds no hardcoded colors. Each widget calls theme::ink() and similar functions. This one rule lets t repaint the whole app, including the markdown stylesheet. Keep it.
